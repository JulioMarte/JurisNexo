# JurisNexo — Current Ingestion, Resolution, and Parser Status

## 1. Purpose

This document is the factual implementation snapshot for the corpus-ingestion path as of 2026-09-11. It distinguishes what is merged and deployed from what is experimental or still incomplete.

The governing rule is simple:

> JurisNexo must not promote uncertain parsed data into canonical legal facts without preserving the exact source evidence, parser/resolver identity, and decision trail that produced it.

## 2. Implemented and deployed database chain

The deployed corpus path currently supports:

```text
primary source artifact
    -> artifact pages
    -> ingestion job + parser version
    -> metadata observations
    -> immutable metadata resolution
    -> future promotion event
    -> canonical cases.*
```

The system deliberately does **not** implement either of these shortcuts:

```text
parser -> cases
observations -> resolver -> UPDATE cases without ledger
```

### 2.1 `0004_ingest_observations`

Introduced:

- `corpus.parser_versions`;
- `corpus.ingestion_jobs`;
- `corpus.case_metadata_observations`.

Observations are evidence-bearing candidates, not canonical facts.

### 2.2 `0005_composite_fk_coverage`

Added missing covering indexes for composite provenance foreign keys.

### 2.3 `0006_ingestion_artifact_prov`

Closed a critical provenance hole. PostgreSQL now proves that an observation:

- belongs to the stated case;
- cites a `case_page` belonging to that case;
- cites a page belonging to the same artifact;
- uses exactly the artifact processed by the ingestion job.

Cross-case, cross-artifact, and job/artifact mismatch writes are rejected by the database.

### 2.4 Observation persistence adapter

The SCJ deterministic page parser can now produce `MetadataObservation[]` and persist them idempotently using:

```sql
ON CONFLICT (ingestion_job_id, observation_key)
DO NOTHING
```

The adapter is covered by real PostgreSQL tests for typed values, offsets, idempotent retry, missing page mappings, artifact mismatch, and database contracts.

### 2.5 `0007_resolution_ledger`

Introduced immutable-in-practice resolution records:

```text
corpus.case_metadata_resolutions
corpus.case_metadata_resolution_observations
```

Each resolution records:

- case;
- field;
- typed resolved value when one exists;
- resolution status;
- resolver name/version;
- code revision;
- idempotency key;
- exact supporting/conflicting/selected observations.

PostgreSQL prevents a resolution for case A from attaching an observation owned by case B.

`conflicting` and `unknown` resolutions cannot carry a canonical value. Eligible resolution states must carry exactly one typed value.

Promotion state is intentionally **not** stored by mutating a resolution row.

### 2.6 `0008_quarantine_legacy_public`

The old Supabase prototype schema under `public` was audited before external demo use.

Findings before hardening included:

- 22 legacy application tables with broad direct privileges for `anon` and `authenticated`;
- two tables with RLS disabled;
- seven client-executable legacy RPCs;
- two client-executable `SECURITY DEFINER` functions;
- mutable function `search_path` settings.

The legacy application tables were empty, so the correct action was quarantine rather than preserving an obsolete client API.

The migration now:

- enables RLS on known legacy tables when they exist;
- revokes direct table privileges from `anon` and `authenticated`;
- revokes legacy RPC execution from `PUBLIC`, `anon`, and `authenticated`;
- pins legacy function `search_path`;
- retains the old objects only for rollback/forensic reference.

Production verification confirmed zero direct `public` table grants for the two client roles and no client execution privilege on the seven inventoried legacy RPCs.

## 3. Reproducible backend dependencies

`backend/uv.lock` is now generated by `uv`, committed, and enforced.

Docker runtime/test images use frozen installs. A future build of the same commit no longer silently re-resolves dependency versions from loose version ranges.

This closes the previous reproducibility gap represented by issue #7.

## 4. Current SCJ parser reality

The existing production parser is intentionally narrow. It extracts page-level observations for patterns such as:

- `SCJ-...` decision numbers;
- labeled `Expediente núm.` values;
- `Partes`;
- `Materia`;
- `Decisión`;
- `Ponente`;
- a specific long-form decision-date formula.

That parser is **not yet trustworthy as a complete SCJ metadata parser**.

## 5. Real-corpus benchmark findings

A reproducible GitHub Actions profiler was executed against seven distinct modern Supreme Court compilations already present in JurisNexo Storage:

```text
2023 Jan-Apr
2023 May-Aug
2023 Sep-Dec
2024 Jan-Apr
2024 May-Aug
2024 Sep-Dec
2025 Jan-Apr
```

Together these contain 4,494 physical PDF pages.

### 5.1 2025 publication generation

For `Principales_Decisiones_enero_abril_2025.pdf`:

- 1,031 pages;
- SHA-256 `c32cf2bcad0325c8fbe49f27f7da39d50ef6b1430fe72b4e84f3006148f87dc2`;
- 1,017 pages recognized by the experimental structured-header detector;
- 14 pages not recognized;
- 41 candidate contiguous case runs after correcting repeated-header and incidental-citation errors.

Observed layout families included:

- Primera Sala;
- Segunda Sala;
- Tercera Sala;
- Pleno/resolution-style material.

The existing page metadata parser coverage over those 41 candidate runs was approximately:

| field | candidate runs with field | coverage |
| --- | ---: | ---: |
| decision number | 39 | 95.1% |
| decision summary | 18 | 43.9% |
| matter | 18 | 43.9% |
| rapporteur | 8 | 19.5% |
| parties | 6 | 14.6% |
| decision date | 6 | 14.6% |
| docket number | 3 | 7.3% |

These numbers are **coverage, not precision/recall**. They do not imply that the extracted values are correct until a gold review is performed.

### 5.2 2023–2024 publication generations

The same 2025-oriented structured-header detector recognized exactly zero pages across the six 2023–2024 compilations.

This is not interpreted as “no cases found.” Inspection of the extracted text shows a materially different editorial generation, including case headings such as:

```text
SENTENCIA DEL 29 DE FEBRERO DE 2024, NÚM. SCJ-SS-24-0138
```

rather than the repeated 2025 structured metadata headers.

Therefore:

> A single timeless `SCJ parser` is not a credible abstraction.

The parser must support versioned/layout-specific publication families and must preserve `unknown/review_required` when a page or segment cannot be classified reliably.

## 6. Important parser lessons already demonstrated

### 6.1 A decision number occurrence is not a boundary

The initial profiler incorrectly treated repeated `SCJ-*` occurrences as candidate case starts. The 2025 compilation repeats case headers across pages, and body text can cite other SCJ decisions.

Boundary detection must operate on stable layout identity and contiguous page runs, not on arbitrary legal-reference matches.

### 6.2 Structured layout signals outrank incidental citations

A Tercera Sala decision cited `SCJ-PS-23-1258` near the top of one page. A naive number-first classifier created a false Primera Sala split.

The corrected experimental detector gives chamber/layout grammar precedence over incidental decision-number references.

### 6.3 Date extraction is currently materially incomplete

Segunda Sala 2025 pages expose labels such as:

```text
Fecha: 28 de febrero de 2025
```

while the current production page parser primarily recognizes the longer formula surrounding `dicta la siguiente sentencia`.

The low measured date coverage is therefore a parser limitation, not evidence that dates are absent from the source.

### 6.4 Publication-generation changes are first-class

2023/2024 and 2025 compilations require different segmentation/extraction grammars. Historical expansion will likely reveal further generations.

Every supported layout family therefore needs:

- a stable layout/parser identifier;
- versioned rules;
- fixtures drawn from real primary-source pages;
- explicit supported date/document ranges only when empirically justified;
- evaluation results;
- fallback to `unknown` when no known layout wins safely.

## 7. Promotion remains intentionally incomplete

The correct target architecture is:

```text
observations
    -> resolver
    -> immutable resolution
    -> immutable promotion event
    -> canonical cases.*
```

A draft `0009` decision-date promotion design exists outside `main`, but promotion is **not considered complete** until:

- the migration contract is reviewed against current `main`;
- a transactional persistence/promotion adapter exists;
- only explicitly promotable resolution states may update `cases.decision_date`;
- resolution value and promoted value must agree;
- selected evidence must exist for automatic promotion;
- same-case provenance is enforced;
- retry/idempotency and adversarial tests pass;
- the full path is merged and deployed.

Do not document `0009` as deployed until those conditions are true.

## 8. Current release gate for parser trust

The parser may be used for exploratory profiling before it satisfies this gate, but automatic canonical promotion should remain restricted until a representative gold dataset demonstrates acceptable quality.

Required evaluation dimensions:

- case-boundary precision/recall;
- decision-number precision/recall;
- docket/expediente precision/recall;
- decision-date precision/recall;
- court-organ precision/recall;
- page-span correctness;
- conflict rate;
- manual-review rate;
- unknown-layout rate.

Metrics must be reported per layout/publication generation as well as globally. A high global score must not hide a broken chamber or year.

## 9. Next implementation sequence

The correct next order is:

```text
freeze/document current benchmark evidence
    -> introduce versioned SCJ layout detector contract
    -> implement 2023/2024 publication-generation parser
    -> implement/refactor 2025 layout-family parsers
    -> segment by contiguous stable header identity
    -> parse layout-specific metadata
    -> emit common MetadataObservation contract
    -> add real-page golden fixtures
    -> generate stratified human-review sample
    -> measure precision/recall
    -> improve deterministic rules
    -> only then evaluate LLM fallback on unresolved cases
    -> finish immutable promotion event path
    -> begin canonical pilot ingestion
```

Embeddings, rerankers, and general research-agent work remain downstream of trustworthy case segmentation and legal metadata.

## 10. Honest interpretation

The ingestion architecture is substantially stronger than a conventional PDF-to-vector-store pipeline because it makes provenance, contradiction, and promotion explicit.

However, the source parser is not yet complete enough to justify mass canonical ingestion. The seven-compilation benchmark demonstrated that directly: a detector tuned to the 2025 publication generation completely misses the 2023–2024 generation.

That failure is useful evidence. The next milestone is not “more AI.” It is a parser architecture that can prove which publication grammar it recognized, what evidence it extracted, what it could not resolve, and how accurately those decisions match human-reviewed source pages.
